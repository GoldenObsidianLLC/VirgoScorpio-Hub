# F1.74 Password-Reset Queue Threat Model

**Status:** implementation threat-model note for F1.74 / PR #306
**Scope:** public password-reset request acceptance, PostgreSQL queue processing, identity-token issuance, mail-outbox handling, and the mail worker.
**Assurance boundary:** this is an engineering design note, not an independent security assessment, penetration test, or production certification. Independent tenant isolation and platform security reviews remain tracked by issues #14 and #25.

## Assets and security objectives

| Asset | Objective |
|---|---|
| User accounts and authentication state | Prevent unauthorized password changes and account enumeration. |
| Reset tokens and reset URLs | Keep tokens unpredictable, short-lived, confidential, single-use, and absent from logs. |
| Email addresses and queue metadata | Minimize retention and limit exposure. |
| Queue and mail-outbox availability | Bound resource use, preserve accepted work, and recover from worker interruption. |
| Provider credentials and delivery | Keep secrets outside source control and distinguish queued work from provider-confirmed delivery. |

## Trust boundaries and actors

The public API is exposed to unauthenticated requesters and automation. The API writes to PostgreSQL; the separately supervised mail worker claims queue work and writes identity-token and mail-outbox rows. The mail provider and recipient mailbox are external trust domains. Database operators, backups, and anyone with database read access are privileged actors because pending mail-outbox payloads contain a deliverable reset URL.

## Threats, mitigations, and residual risk

| Threat | F1.74 controls | Residual risk / follow-up |
|---|---|---|
| Account enumeration | Production route returns the same generic accepted response; API does not perform an account lookup before enqueue. Active-user lookup happens in the worker. | Timing and provider/mailbox behaviors require live external E2E assessment. |
| Request flooding and storage exhaustion | Existing per-IP limiter; PostgreSQL transaction-scoped advisory lock; shared 120-second normalized-target cooldown; bounded pending/processing capacity (default 5,000, configurable 1–100,000); eight-attempt limit; terminal retention cleanup. | One global capacity lock serializes enqueue checks and may constrain throughput. Load/soak and fault-injection acceptance remains required under #24. |
| Accepted request lost during API/worker crash | API waits for committed queue row before returning 202. Worker claims with `FOR UPDATE SKIP LOCKED`; stale processing claims recover after five minutes. Token-hash creation, mail-outbox insertion, and queue completion share one transaction. | Delivery is at-least-once. A worker crash after provider acceptance but before the sent-state update can cause a duplicate email; provider idempotency is not established here. |
| Duplicate reset requests invalidate or amplify tokens | Shared target cooldown across API replicas, per-user transaction-scoped advisory lock for token issuance, recent-token check, and consumption of previous unconsumed reset tokens. | The advisory-lock and cooldown design still requires real concurrency/load verification beyond the hosted integration scenarios. |
| Token theft from action-token storage or logs | Reset token is generated from cryptographically secure random bytes; `identity_action_tokens` stores only the SHA-256 digest; link expiry is 30 minutes; expired/missing/invalid expiry metadata is rejected by the mail worker; structured logs omit target email and reset URL. | SHA-256 protects the database token verifier but is not encryption of the mail payload. |
| Exposure of a pending reset URL | Raw URL remains in `mail_outbox.payload` only while delivery is pending or retryable; payload is cleared after successful send, expiry, or terminal failure. Terminal stale recovery also clears the payload. | Database readers, provider systems, recipient mailboxes, and database backups may still expose a pending link. Database access controls, at-rest encryption, backup retention, provider security, and mailbox security are outside this implementation increment. |
| PII over-retention | Queue target email is cleared after the 120-second cooldown; terminal queue rows are pruned after 24 hours; logs use bounded low-cardinality fields and sanitized error codes. | Cleanup is worker-driven and can be delayed while the mail worker is stopped. The existing mail-outbox recipient column follows its existing retention policy and is not removed by this increment. |
| Expired or malformed reset link delivered | Worker fails closed when a password-reset payload has missing, invalid, or elapsed `expiresAt`; it terminalizes and clears the payload. | Provider delivery and bounce confirmation are separate operational gates. |
| Provider/worker outage | Bounded retry/backoff, terminal failure after eight attempts, stale-claim recovery, and queue depth/age/terminal-failure snapshots. | Queue acceptance does not prove email delivery. Sender authentication, production provider credentials, bounce handling, alert routing, and live identity/email acceptance remain open gates. |
| Operational misconfiguration | Capacity config is validated; worker is a separate supervised process with a systemd reference unit; production developer-token mode is explicitly prohibited. | The systemd unit is a reference only and has not been installed or qualified on a target host. OTLP routing, secret-file permissions, alert thresholds, and ownership need deployment-specific validation. |

## Operational signals

The mail worker emits `virgoscorpio_hub.password_reset_queue.snapshot` approximately every 30 seconds through the existing structured OTLP log pipeline. Fields are bounded counts/age/capacity: pending, processing, failed in the last 24 hours, oldest pending age, and configured capacity. Snapshot failures are fail-open and log only a sanitized error code.

Route the structured event to the approved OTLP backend and alert on sustained oldest-pending age, capacity saturation, terminal failures, mail-provider errors, and worker restarts. A local structured log event is not proof that a production backend, dashboard, alert, or on-call owner exists.

## Release dependencies and evidence

Before production consideration, retain exact-candidate evidence for:

1. Supported Node 22/24 CI, CodeQL, browser checks, and hosted PostgreSQL integration including fresh/idempotent migration 0022 and the new queue integration tests.
2. Deployment-specific mail-worker supervision, secret provisioning/permissions, OTLP routing, queue alert thresholds, rollback, and incident ownership (#26).
3. Live provider authentication/delivery/bounce and identity/email E2E.
4. Load/soak, queue saturation, worker restart, database/provider outage, and backup/restore exercises (#24).
5. Independent tenant-isolation and platform security assessments (#14 and #25).

Passing F1.74 tests or PR checks does not close those production gates. This document records the implementation's current threat model and residual risks; it does not certify production security.
