# F1.75 — Community Message Membership-Revocation Threat Model

**Status:** open [PR #308](https://github.com/GoldenObsidianLLC/VirgoScorpio-Hub/pull/308), ready for review and rebased onto `main` SHA `5eb906efdd3413cfd8851506f6863daa8afa0dfc`; rebased implementation commit `c9b52f4b805891715359a485cf79df196a892d10`.
**Parent tracking:** [issue #124](https://github.com/GoldenObsidianLLC/VirgoScorpio-Hub/issues/124) remains open.
**Scope:** site-member authorization for community conversation message creation, and reuse of the existing moderation transaction revalidation.

## Security objective

A user must still be an active member of the selected site at the point a protected community mutation commits. A successful request-level membership check is only a preflight decision; it cannot authorize a later database write after a concurrent membership, account or role change.

The database remains the authority. No Redis/cache copy of membership is used for this decision.

## Assets and trust boundaries

- Site-scoped community conversation membership and message content.
- Site membership, account-active state and role capabilities.
- Message notification rows and downstream consumers of those notifications.
- The boundary between request parsing/routing and the later PostgreSQL mutation transaction.
- The privileged site-member removal path in `packages/auth/src/service.js`.

## Threat: authorization time-of-check/time-of-use race

1. A signed-in actor passes request preflight, which resolves the site and checks current site membership.
2. Request parsing, validation or route dispatch takes place.
3. An administrator removes the actor from the site and commits the membership deletion.
4. The original request continues. Conversation membership may still exist independently of site membership.
5. Without a transaction-time site-membership check, the actor could insert a message and notification after site access has been revoked.

Conversation membership is not a substitute for active site membership. The same stale-preflight class also applies to account deactivation and role/capability revocation.

## Transaction and lock-order mitigation

The mutation uses a shared authorization helper in `packages/community/src/workflows.js`:

1. Acquire the selected `sites` row `FOR KEY SHARE`.
2. Read and lock the active user, site-membership and role rows `FOR SHARE`.
3. For message creation, lock/validate the conversation and the actor's conversation-member row.
4. Insert the message and any associated notification rows in the same mutation transaction.
5. Commit only if every authorization and domain check passes.

The site-member removal path acquires the same site row `FOR UPDATE` before deleting `site_memberships`. The conflicting row locks serialize removal and message creation. With PostgreSQL's READ COMMITTED isolation, once the message transaction obtains the site lock after a removal commits, its subsequent membership query observes the committed deletion and rejects the mutation before message or notification writes.

Community moderation now calls the same helper for its `community:moderate` capability check instead of maintaining a second copy of the site/user/membership/role lock sequence. Capability semantics remain: the requested capability, `site:manage`, or `*` grants the action.

The lock order is deliberately site-first to agree with member removal and avoid acquiring a conversation lock before tenant authorization is stable.

## Required invariants

- Request preflight remains useful for early rejection, but is never the only membership authorization for this message mutation.
- Site membership and active-account status are re-read under locks owned by the mutation transaction.
- A denied/revoked actor cannot persist a message or create its new-message notification.
- Membership, account and role changes cannot overtake a protected mutation after its shared locks have been acquired.
- Moderation keeps its current capability policy and performs the check inside the mutation transaction.
- The existing non-production developer bypass remains unchanged; it is not a production authorization mechanism.
- Errors fail closed as HTTP 403; no message text or conversation data is returned to an actor who no longer has site access.

## Regression coverage

- Unit tests verify site-first lock acquisition, membership read before conversation/member locks and message insertion, rejection/rollback for an absent active membership, and developer-bypass compatibility.
- The PostgreSQL integration regression holds the site row `FOR UPDATE`, deletes the actor's membership without committing, starts a message request after preflight succeeds, and observes the competing `FOR KEY SHARE` wait. After committing removal, it asserts HTTP 403 and zero message/notification rows.
- Hosted PostgreSQL CI must execute this race test with zero skips on the final rebased PR head. Local PostgreSQL was not configured during candidate validation, so the live race has not yet been locally exercised.

## Scope boundaries and residual work

This increment secures the message-creation transaction and consolidates the existing moderation revalidation. It does not certify every community mutation or close the broader tenant-isolation assessment. Other community routes that rely on request preflight still need source-by-source review for stale authorization between preflight and mutation.

The implementation assumes site membership removal continues to take the parent site row `FOR UPDATE` before deleting the membership. Any future removal path or bulk membership operation must preserve this lock order. A new authorization-bearing mutation should call the shared helper before acquiring domain-specific row locks, then add focused unit and PostgreSQL concurrency coverage.
