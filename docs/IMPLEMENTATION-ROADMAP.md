## Addendum — 9 November 2026 (F1.20 Redis outage/recovery qualification)

F1.20 carries the reconnect resilience work beyond deterministic retry-policy tests. The policy is extracted once and reused for both bridge publisher/subscriber clients and the Redis-backed presence client. Both Redis client paths disable offline command queues. Bridge Pub/Sub sends fail fast while the publisher is not ready, preserving same-instance local-first delivery but not queueing ephemeral remote notifications; Redis presence reads/writes fail closed while the client is not ready, avoiding stale lease commands being replayed after a reconnect.

A dedicated live integration test is added for a real Redis stop/start cycle. It requires a credential-free loopback Redis URL and the exact full container ID of one approved running `redis:7.4-alpine` container. CI maps the service on loopback port 6379; a local reproduction may use a new disposable container mapped to an explicitly assigned, stable loopback-only host port. The test validates container identity/image/state before fault injection, waits for publisher/subscriber and presence reconnect attempts to exceed the previous ten-retry cutoff, verifies readiness/degraded metric recovery, ensures outage-time Pub/Sub notifications are not replayed, and checks refreshed site-scoped presence snapshots. A companion PostgreSQL-backed browser scenario revokes membership while the same physical Redis outage is active; the remote idle WebSocket must close through the existing PostgreSQL heartbeat reauthorization fallback and no revoked collaborative operation may be committed. The test restores the exact container in `finally`, while CI also has an `if: always()` service recovery step. Both safety gates are scoped to this dedicated disposable service; no developer/shared/remote Redis endpoint is stopped or mutated.
